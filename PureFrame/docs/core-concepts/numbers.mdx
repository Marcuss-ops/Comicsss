# Numbers

In PureFrame, animation starts with numbers.

A spring returns a number.
An interpolation returns a number.
An easing curve returns a number.
A noise function returns a number.

Those numbers are then used to drive Canvas rendering.

This is one of the core ideas of PureFrame:

**frame in, numbers out, draw calls next**

PureFrame does not depend on browser layout, CSS transitions, or DOM state during final rendering.
Instead, each frame resolves to explicit values that can be used for position, scale, rotation, opacity, blur, stroke width, glow intensity, audio volume, or any other renderable property.

## Why this matters

Thinking in numbers makes animation composable.

You do not need a special primitive for every motion pattern.
You can build motion by combining smaller values.

Examples:

- add values to stack motion
- subtract values to create exit behavior
- multiply values to control intensity
- clamp values to keep them in range
- remap values from one domain into another

This fits the PureFrame model well:
no hidden state, no browser-driven animation loop, just deterministic values for the current frame.

## Common sources of numbers

In PureFrame, numbers usually come from these places:

- frame-based progress
- springs
- interpolation
- easing functions
- oscillation
- noise
- audio-driven signals
- external timing data converted into frames

## Enter and exit

A common pattern is to build one value for entering and another for leaving, then combine them into a single output.

```ts
import { spring } from "@pureframe/core";

type ScaleArgs = {
  frame: number;
  fps: number;
  durationInFrames: number;
};

export const resolveScale = ({
  frame,
  fps,
  durationInFrames,
}: ScaleArgs): number => {
  const enter = spring({
    fps,
    frame,
    config: {
      damping: 200,
    },
  });

  const exit = spring({
    fps,
    frame,
    durationInFrames: 20,
    delay: durationInFrames - 20,
    config: {
      damping: 200,
    },
  });

  return enter - exit;
};
```

At the beginning, enter starts near 0 and moves toward 1.

Near the end, exit also moves from 0 to 1.

By subtracting exit from enter, you get a single number describing the visible state of the element across the full composition.

## Using the value in Canvas 2D

The important difference in PureFrame is that the number is not used to style a DOM node.
It is used to drive a draw call.

```ts
type DrawBoxArgs = {
  ctx: CanvasRenderingContext2D;
  frame: number;
  fps: number;
  durationInFrames: number;
  width: number;
  height: number;
};

export const drawBox = ({
  ctx,
  frame,
  fps,
  durationInFrames,
  width,
  height,
}: DrawBoxArgs) => {
  const scale = resolveScale({ frame, fps, durationInFrames });

  ctx.save();
  ctx.translate(width / 2, height / 2);
  ctx.scale(scale, scale);

  ctx.fillStyle = "#4290f5";
  ctx.beginPath();
  ctx.roundRect(-50, -50, 100, 100, 20);
  ctx.fill();

  ctx.restore();
};
```

The renderer does not guess anything.
It receives explicit numbers and applies them.

## Numbers drive everything

Animation values are not limited to transforms.

A single frame can resolve many values:

```ts
const enter = spring({ fps, frame });
const exit = spring({
  fps,
  frame,
  durationInFrames: 20,
  delay: durationInFrames - 20,
});

const scale = enter - exit;
const opacity = Math.max(0, Math.min(1, enter * 1.2 - exit));
const rotation = enter * 12 - exit * 12;
const y = 80 * (1 - enter) + 40 * exit;
const glow = enter * 24;
const blur = (1 - enter) * 18;
```

Each of these is just math on frame-derived values.

## A useful mental model

A good way to structure PureFrame code is this:

1. resolve numbers from the current frame
2. combine the numbers into final motion values
3. pass those values into Canvas rendering

This keeps code clean and predictable.

A renderer should consume numbers.
A motion resolver should produce numbers.
A timing primitive should only describe how numbers evolve across frames.
